# Pixel technical notes

Last updated 2026-10-11 (after the first build session). The plan of record is [plan.md](plan.md); this file holds implementation details and gotchas that don't belong in the plan.

## Mount layout inside an agent VM

- Share 1: host `/srv/pixel/workbases` → guest `/workbases`, **readonly** (virtiofs).
- Share 2: host `/srv/pixel/workbases/<run>` → guest `/workbases/<run>`, read-write, mounted on top of share 1.
- Read-only must be enforced on the host side; the agent is root in the guest.
- Nested mount (share 2 on top of share 1) is expected to work; verify in phase 0.

## opencode inside the VM

- Pinned version, installed in `pixel-image`.
- Global config allows every permission so it never blocks on approval (bash, edit, webfetch, external_directory and any others the pinned version has). Check the exact keys against the pinned version's config schema.
- `opencode serve` as a systemd unit, password-protected (`OPENCODE_SERVER_PASSWORD`), listening on the VM's bridge address. `Restart=` is **off**: Pixel decides restarts so it can send the right continue message.
- Pixel also auto-approves any `permission` request event as a safety net.
- OOM detection: `systemctl show opencode -p Result` = `oom-kill`, or a kernel OOM log line naming the opencode process. If the OOM killer hits a build/fuzzer instead, opencode just sees a failed tool call; nothing to do.
- Resume after restart: sessions persist on the VM disk, so Pixel continues the same session ID.

## Pixel container

- Host networking, to reach VMs on `incusbr0` directly.
- Mounts the Incus unix socket (root-equivalent on the pixel host; fine, Pixel is trusted) and `/srv/pixel`.

## Single runtime (one container)

`PIXEL_RUNTIME=single`, built from `Dockerfile.single` / `compose.single.yaml`. `runtime/process.ts` holds what it shares with `local` (opencode as a child process, launch info, restart).

- **Users**: each run gets uid 20000+ from a counter in `machines/.launch/next-uid`; uids are never reused because workbases keep their owner. `/etc/passwd` lives in the image, so `ensureUser` recreates the user (same uid) before every opencode start. On delete, the workbase is chowned to root (still readable, frozen) and the user removed.
- **Command wrapper**: `choom -n 500` (killed before Pixel under memory pressure) → `nice 10` → `ionice -c2 -n7` → `prlimit --nproc --core=0` → `setpriv --reuid/--regid --clear-groups --no-new-privs`. The agent environment is built from scratch, so Pixel's env (`PIXEL_PASSWORD`) never leaks.
- **Permissions**: data dir 0711, `machines/` 0711, `workbases/` 0755, history/transcripts/`.launch` 0700, `pixel.db*` 0600, each run dir 0700 (agent), each workbase 0755 (agent). The backup copy of the database is created 0600 before `VACUUM INTO`.
- **Limits without cgroups** (an ordinary container can't create them): memory is checked every 5 s by summing RSS over the uid's processes; over the run's size the largest process gets SIGKILL and the timeline gets a `limit` entry. Disk is `du -sxb` of the run dir (cached 5 min) against the run's disk size, reusing the watchdog's disk-full rule. CPU is only priority; the container's `cpus` is the real cap.
- **Firewall**: iptables `OUTPUT -m owner --uid-owner 20000-59999 -j PIXEL_AGENTS`, which rejects 10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10 (and fc00::/7, fe80::/10) and the dashboard port on loopback, but allows the resolv.conf nameservers on port 53. Needs NET_ADMIN; failure is reported in `info()` on the System page, not fatal.
- **Stopping** kills every process of the uid (fuzzers, servers), not just opencode. tini is PID 1 so orphans get reaped.
- **Free-disk guard** (all runtimes): the watchdog stops runs when the data disk has less than `PIXEL_MIN_FREE_GIB` free. Tests set it to 0.
- Verified 2026-10-11 in a slim test container (fake opencode): users and permissions as above, agent→dashboard blocked, private-range rules in place, internet allowed, memory kill + OOM recovery, container restart → reattach and continue. Not verified: the full image build, real opencode as an agent user, gdb/ptrace under Docker's default seccomp, Coolify honouring `cap_add`/`cpus`/`mem_limit`/`tmpfs`.

## Known gotchas

- **Nested virtualization**: the pixel host VM on Proxmox needs CPU type `host` and nesting enabled on the node (`kvm_intel nested=1` / `kvm_amd nested=1`).
- **Docker and Incus on the same host**: Docker sets the iptables FORWARD policy to DROP, which breaks Incus bridge networking. Fix: `"ip-forward-no-drop": true` in Docker's `daemon.json` (or `DOCKER-USER` accept rules for `incusbr0`).
- **VM memory** is mostly held once the guest touches it; keep total `limits.memory` within the 16 GB. Each VM costs ~0.5–0.7 GB fixed ([benchmarks/incus-research-2026-10-11.md](benchmarks/incus-research-2026-10-11.md)).
- **ZFS storage pool**: cap the ARC (`zfs_arc_max`), or it eats RAM inside the 16 GB.
- **VM disks** only grow; Incus default is 10 GiB, Pixel sets 20 GiB.
- **opencode updates** are frequent; bump the pinned version deliberately and rebuild the image.

## Machine size on the fly and disk rescue (runs/resize.ts) — added 2026-10-20

- `POST /runs/:id/size {cpu?, memoryGiB?, diskGiB?}` changes a live run's size (`Runtime.resize`): single updates the memory limit at once and the disk limit at the next metrics; CPU there is only a priority. Incus PUTs `limits.cpu`/`limits.memory` (hotplug) and grows the root disk; a smaller disk can't shrink a VM, so `metrics()` reports min(df size, run size) and the watchdog holds the run to it. Local records the size only.
- Disk rescue, in the watchdog's metrics pass (`checkDisk`): a running run whose disk passes `diskFullPercent` gets `diskRescueGiB` extra (`runs.disk_boost` = {baseGiB, extraGiB, at, by}), its step is aborted and `diskRescueMessage` sent (in the run's serial queue). Under the goal (90% of the stop point on the normal disk) the disk goes back and the agent just carries on; filling the extra too, or `diskRescueMin` passing, stops the run. `runs.disk_rescues` counts automatic ones against `diskRescueMax` (reset with the counters). `POST /runs/:id/disk-boost` does the same by hand (resumes a stopped run with the message), `DELETE` ends it; setting the disk in the size dialog ends a boost.
- The single runtime measures disk with du every minute (not 5) while a boost is on, so the cleanup shows.
- Stop/idle race fixed the same day: stops (watchdog, Stop button) used to abort before marking the run stopped, so the idle the abort caused could send "continue your work" to a stopped run (and wipe its reason). Stops now mark first, and `onIdle` re-checks the status after its await.
- Untested on Incus: whether a VM's filesystem grows with its root disk live (needs a resize inside the guest otherwise; the min() above keeps the watchdog right either way), and hotplug on the pinned Incus.

## opencode API notes (2.1.0)

- Client: `server/src/opencode.ts`; translation to Pixel's stored shape: `server/src/opencodeShape.ts` (see decisions.md 2026-10-20, opencode 2). Every request carries `directory` and `location[directory]`; answers are wrapped in `{data}`.
- Events: `GET /api/event` sends `data: {id, created, type, data}`. Durable events (`session.created`, `session.step.*`, `session.text.started/ended`, `session.tool.*`, `session.execution.*`, ...) build the messages; `session.text.delta`, `session.tool.progress`, `session.usage.updated` are live only. No `session.status`/`session.idle`: busy = `session.execution.started`, idle = `succeeded`/`failed`/`interrupted` (reason `superseded` means a newer prompt took over). The translator emits 1.x-style `session.status`, `session.idle`, `message.updated`, `message.part.updated`, `message.part.delta`, `todo.updated`, `question.*`, `permission.*`, plus `tool.input.delta` (counted for tokens/s only).
- Messages: `GET /api/session/:id/message?order=asc&limit=` pages with `cursor.next`. Types user, synthetic, system, skill, shell, assistant (one per model call, `content` = text/reasoning/tool in the order they started), compaction, idle and switch markers. Tool states streaming/running/completed/error; output is `content` (text items); `running` keeps `metadata: {}` in storage, the shell id only comes in `session.tool.progress`.
- Model and thinking level live on the session (`POST /api/session/:id/model {model: {providerID, id, variant}}`); `prompt` switches first when they differ. `POST /api/session/:id/prompt {text, delivery}`: steer (default) or queue.
- `GET /api/session/active` lists running sessions; children via `GET /api/session?parentID=`; questions are forms (`/api/form`, reply `{answer: {q0: ...}}`, cancel `DELETE ...?message=`); permissions `/api/permission/request`, reply `{decision}`; models with limits and variants `GET /api/model` (only providers it can use).
- PTY: `/api/pty`, connect at `/api/pty/:id/connect` with basic auth; opencode adds `-l` itself; text frames starting with `\x00` are control messages and are not passed to the browser.
- Shell output of a running tool call: `GET /api/shell/:id/output?cursor=&limit=` (byte cursor; `size` is the total so far).
- Config: opencode 2 reads 1.x config shapes too, but provider entries are written natively (`opencodeConfig.ts`). `permission: "allow"` still allows everything. `share` is accepted.

## Subagents

- Subagents are `subagent`-tool child sessions (`parentID` = caller), shown as `task` calls in Pixel. `syncTranscript` follows them via `GET /api/session?parentID=`. They can run in the background; `onIdle` waits while any child of the run is active.
- Interrupted subagents: opencode 2 ends them as "Tool execution interrupted (sessionID: ...)"; the `resume-subagents` plugin adds, in the model's copy only, a hint to resume that session with the subagent tool's `sessionID`, on the latest interrupted call per child unless a later call already resumed it. Tested in `server/test/plugin.test.ts` and in a real opencode 2.1.0.

## Dashboard telemetry (fleet.ts)

- `/api/fleet`: one snapshot for every non-archived run: output tokens/s samples (90 × 1 s; live from streamed deltas, corrected to exact counts when each call finishes), latest tool call per session (with status, so "thinking…" shows between calls), subagents with state from their task calls, 60 × 30 s activity buckets (dominant kind; "alert" where Pixel recovered or a limit fired), CPU/mem/disk from the last metrics row, context used (latest assistant message with token counts) and the model's context limit (asked once from opencode `/api/model`), machine name/PID/endpoint. Plus shared memory (cgroup v2 `memory.max`/`memory.current` when limited, else the machine), today's spend and tokens from assistant messages (cost per hour per run, top four plus other; tokens by kind and cache hit rate, both against yesterday up to the same time; projection at the last hour's rate; cached 10 s) and the cross-read graph.
- Live: `fleet.tick` (`*`, every second, tokens per run), `activity` (`*`, on each tool-call status change only), `timeline` now also goes to `*`. The web `lib/fleet.ts` store applies these and refetches every 15 s; `lib/runs.ts` is the shared runs list.
- Cost (2026-10-16): the snapshot reads tool calls from `tool_calls`, a narrow table SQLite triggers on `parts` keep current (tool, status, start/end, task child, interrupted, and only the inputs `describeCall` uses), indexed by run, session and time; never parse `parts.data` for dashboard numbers.
- Pushed, not polled (2026-10-16): the sampler calls `pushFleet` every second. A run is rebuilt when any bus message names it (and every 15 s, since activity buckets age), the fleet-wide part every 5 s; each tab gets one `fleet.patch` with only the changed fields per run (tps stays on `fleet.tick`), removed runs and the top part if it changed. `/api/fleet` returns that state (with live tps) for a tab that connects; without the sampler (tests) it builds. The web store loads the snapshot once (`staleTime: Infinity`), applies patches newer than it, and a hidden tab ignores live updates and reloads once when shown. Updates over 250 ms are logged.
- Writes (2026-10-16): message and part upserts skip unchanged rows (a resync after every stream reconnect re-sends the whole transcript); unfinished parts (running tool calls, streaming text) are stored at most every 5 s, finished ones at once, the dashboard still gets every update live; `flushPartWrites` on unwatch/shutdown. `message_totals` (triggers on `messages`) holds each run's input/cache read/cache write for the run view. Transcript archive (`archive.ts`): runs finished and quiet for 7 days move their `parts` to `transcripts/<run>/<session>.jsonl.gz` (`{"m": message id, "p": part}` per line), hourly; `tool_calls` rows stay (the `parts_archiving` marker stops the delete trigger); `transcript()` merges file and database, database wins, so a resumed run just works and the next pass folds new parts in. System page → Database → Compact runs VACUUM by hand; its temporary copy goes to `<data>/tmp` (`PRAGMA temp_store_directory`), since `/tmp` is a 512 MB tmpfs in the single container. Upgrades (2026-10-16): `PRAGMA user_version` is the schema version (`SCHEMA` in db.ts, bump it with any migration that drops or rewrites data); below it, the first start saves `pre-upgrade.db` (VACUUM INTO, if free disk allows) before migrating. Clean up (`tidy.ts`, System page): measure, then archive finished runs now, drop old copies, slim or delete finished runs' folders, compact; runs in the background, the page polls `/api/system/tidy`.
- Derived tables (2026-10-16): `model_calls` (one row per assistant message: provider, model, created/completed, tokens by kind, cost, error name), kept by triggers on `messages` like `tool_calls` on `parts`; spend today, tok/s series, run charts, context use, run detail cache totals and the Stats page read it. Never `json_extract` message data for numbers. (`llm_calls` is separate: provider health, first token, key per call, captured live.)
- Freeing waiting runs (2026-10-16, user's rules): `runs/release.ts`. Paused or stopped for `releaseIdleMin` (default 15, 0 = never) and not mid-step → `runtime.release` (process runtimes stop only opencode, leaving the agent's own processes; Incus stops the VM), `runs.asleep = 1`, timeline `sleep`. `restartOpencode` and Machine → Start clear it; resume and messages already start opencode (`ensureMachine`). The watchdog skips asleep runs; on start, reattach skips them and marks stopped runs on process runtimes asleep (their opencode died with Pixel). Runs asking a question are "running" and never released. `runs.status_at` = when the status last changed (set in `setRun`). UI: a Zzz icon after the status word, "Free memory" in the run menu, a note on the Machine tab, the setting under Settings → Runs.
- Processes (2026-10-16): `runtime.processes(run)` (`runtime/procs.ts`): process runtimes read /proc (local: opencode's tree; single: every process of the agent's uid, so leftovers count), Incus runs `ps` in the VM (its %CPU is a lifetime average). Kind by pid (opencode) or name/command line (language server, MCP, else the agent's). Machine tab → Processes: memory bar by kind, biggest processes, refreshed every 5 s.
- Pixel's own health (2026-10-16): `health.ts` samples every minute, last 24 h in memory: event-loop lag (a 1 s timer's lateness), API request count and slowest, slowest fleet update, rows written (`total_changes()`, statements only), DB and WAL size, RSS, CPU, open tabs. System page → Pixel. Charts use `components/charts/Meter.tsx` (also the Machine tab).
- Transcript download (2026-10-16): the automatic uncompressed `transcripts/<run>.json` export at finish is gone (the database and the archive have it all); Download transcript in the run menu builds it on demand (gzip-encoded JSON). Old export files are left in place; System page → Clean up removes them.
- `/api/runs/:id/lanes?minutes=N`: per-session tool-call segments + marks (subagent done/interrupted dots, Pixel recover/limit/continue ticks on the main lane). `/api/activity?run=&limit=`: recent tool calls + timeline entries (24 h).
- Tool kinds: shell (bash), read (read/grep/glob/list), edit (edit/write/patch/todowrite), task, web, other. Commands are shown with the run's own target/workbase/scratch paths shortened.
- Styling: tokens in `web/src/index.css`; Tailwind's zinc scale is remapped onto the same greys so older pages match. Light by default, dark with the OS.

## Models and providers (providers.ts)
- Live test (`liveTest.ts`, `POST /api/live {model, text, session?, turn}`, `POST /api/live/:session/abort`, `GET /api/live`): one warm throwaway opencode from `scratchOpencode.ts` (shared with the speed test: empty work dir, `permission: "ask"`, agents' credentials). Started on first prompt, restarted when `agentCredentials()` changes, stopped after 10 idle minutes and on SIGINT/SIGTERM. Pixel reads its `/event` stream and publishes `live` bus messages tagged `{turn, session, kind}`: starting, sent, first (server-measured TTFT), part, delta, message (tokens, cost, error), retry, tool (refused at `permission.asked`/`question.asked`), done/error/stopped. The client sends its own turn id so it can match `starting` before the POST returns. A follow-up continues the same opencode session (the model can be switched mid-chat). Live tok/s is chars/4 over time since the first token until the exact count arrives.
- Provider setup (`catalog.ts`, `providerAccounts.ts`): the catalogue is models.dev (`PIXEL_MODELS_URL`), fetched at most daily and cached in `data/models.json`, falling back to opencode's `~/.cache/opencode/models.json`. Accounts live in the settings table under `_providers` (underscore = never sent by `/api/settings`); the API only returns a key hint. `agentCredentials()` builds what runs and the speed test get: `OPENCODE_CONFIG_CONTENT` (merged over any value in Settings env) with an opencode 2 `providers` block (`opencodeConfig.ts`): each account's key as `settings.apiKey` (also API keys from Settings' auth.json), custom endpoints (`aisdk:@ai-sdk/openai-compatible` or `aisdk:@ai-sdk/anthropic`, one context size for all their models) and base-URL overrides; Settings' auth.json is still copied for other logins. Checked against opencode 2.1.0: env config is merged over opencode.json, a config key enables a catalogue provider, and auth.json isn't imported for a fresh data folder. Works for every runtime because it travels as env. Existing runs get new keys on their next opencode restart (`runs/state.ts` `restartOpencode`, which records `creds_hash`); resume or a message to an idle run with a stale hash restarts it on purpose. Routes: `GET /api/catalog`, `GET /api/catalog/:id`, `GET /api/providers`, `PUT|DELETE /api/providers/:id`, `POST /api/providers/discover`.
- Provider variables and request quirks (2026-10-20): accounts hold `vars` (agents' env, over Settings env, under the GitHub card; secret-looking names come back as hints only; PATH, HOME, OPENCODE_*, PIXEL_*, XDG_* refused), `bearer` (provider `options.headers.Authorization = Bearer <the run's key>`, left out for a run with no key; provider Advanced headers merge with it) and `maxCompletionTokens` (`compatibility.maxTokensField: "max_completion_tokens"`; opencode 2 already sends it by default on OpenAI-compatible calls). `cacheKey` is `compatibility.supportsPromptCacheKey`. `${NAME}` in a base URL (or a catalogue `api` such as Cortex's) is filled from `vars`, then Settings env, and written as `options.baseURL`; `connectedProviders().missingVars` lists the unfilled ones. Custom endpoints: `custom.modelApi` holds models on the other API; opencode gets `models[id].package` for them (per-model package, same baseURL, `/messages` vs `/chat/completions` after it; checked on 1.19.0 with npm, written natively since 2.1.0). `knownModel(id)` (catalog.ts) matches custom model ids against the catalogue, makers first, also without a maker prefix (`openai-gpt-5.4` to `gpt-5.4`); prices are never borrowed.
- Snowflake Cortex (checked 2026-10-20 with the user's account, opencode 1.19.0): base `https://<account>.snowflakecomputing.com/api/v2/cortex/v1`, PAT as `Authorization: Bearer` (x-api-key alone is a 401; with Bearer it's ignored). No `GET /models` (404); `POST /api/v2/statements` with `SHOW MODELS IN SNOWFLAKE.MODELS` lists them with the same PAT (`snowflake.ts`, also the key test). Claude models answer on `/messages` with streaming tools, thinking and prompt caching; the 5.5 models only there ("unknown model" on chat). `/chat/completions` never sends a finish_reason for Claude, and OpenAI models there refuse `max_tokens`. opencode 1.19's built-in `snowflake-cortex` loader renames max_tokens to max_completion_tokens on every call, which `/messages` refuses ("max_tokens: Field required"), so Pixel uses a custom provider id. Opus 5.x thinking: only adaptive, `display` is `summarized` or `omitted` (no raw); opencode's Anthropic variants (low to max) send summarized. A 472k-token prompt was accepted on Haiku 5.5, so the catalogue's 1M context isn't capped at 200k. Snowsight's ListModelsForCodingAgentV2 needs a browser session token, not a PAT. Every runtime pushes or copies `opencode-plugins/` when it starts opencode, so no image rebuild is needed.

- Tables (created by providers.ts on import): `llm_calls` (one row per assistant message: provider, model, created, first_token, completed, tokens, cost, error), `provider_events` (ratelimit / error / retry, with message), `speedtests`.
- Capture in events.ts: `message.updated` → `onMessage` (upsert call; errors become provider events, 429 / "rate limit" text → ratelimit); first `message.part.updated` or `message.part.delta` of an assistant message → `first_token`; `session.status` retry → `onRetry` (deduped per session + attempt). Live `provider` events go to `*`.
- Health (`/api/providers/health?minutes=`): per provider/model: calls, time to first token p50/p90, output tok/s p50 (calls with ≥ 30 output tokens), errors, rate limits, retries, tokens and requests per minute (last 5 min), 12-bucket series, state ok/degraded/limited/idle. Limits per "provider/model" live in settings `providerLimits` (edited on the Models page).
- Leaderboard (`/api/providers/leaderboard`): per `runs.model`: finish rate (report written vs stopped/failed), median duration, tokens/cost per run, continues/OOM per run, real-findings rate from triage verdicts ("real findings", "partly real"), cost per real finding, plus call medians.
- Speed test (`POST /api/speedtests {models}`, `GET /api/speedtests` → results plus the running batch's models and current model): spawns `config.opencodeBin serve` in `data/speedtest/run-*` with only PATH/HOME/LANG/XDG + Settings agentEnv/auth.json and an empty work folder. Config `permission: "ask"`; while a call runs Pixel rejects every permission request and question, and a call that tried a tool is recorded as failed. Models are checked against `/api/model` first. Fixed ~250-word prose prompt, sent async and followed on the event stream until idle; records TTFT (first text delta), total, output+reasoning tokens, tok/s, all on Pixel's clock. Needs opencode in Pixel's container (true for local/single, not for the incus Dockerfile).
- **opencode's gateways (Zen free models, Go) only accept requests that look like opencode's own**: denying permissions in config, or switching off even one tool per request, gets `403 FreeTierError: "OpenCode's free tier can only be used from within OpenCode"`. That's why the speed test keeps every tool and refuses them by permission instead. Anonymous free-tier use from a fresh HOME works. (Tested 2026-10-11, opencode 1.18.23.)
- `opencode serve` 1.18.23 can ignore SIGTERM after a call; the speed test waits 5 s then SIGKILLs.
- First token is Pixel's clock (first part event) minus the message's `time.created` (opencode's clock). Same machine for local/single; on Incus it depends on the VM clock being in sync with the host, plus event-stream latency.
- Checked with a real big-pickle run (15 calls): health first token p50 1.8 s / p90 2.8 s, 149 tok/s; per-call tokens add up to the run totals; leaderboard shows the run as finished. Speed test on big-pickle: 114–124 tok/s, first token 2.5–3.5 s.

## Recovery details

- `onIdle` and `recover` run serialised per run, so an idle event and a watchdog check can't both act.
- Missed events (stream drop, Pixel restart) are caught by the watchdog: busy per our DB but absent from `/session/status` for 60 s → treated as idle; pending permissions are polled and approved.
- opencode unit uses `OOMPolicy=continue` so a fuzzer hitting the OOM killer doesn't stop opencode. When opencode itself is OOM-killed the unit sees SIGKILL (`ExecMainStatus=9`); Pixel confirms with the kernel log (`Killed process … (opencode)`).
- Process runtimes (local, single): SIGKILL of the opencode process counts as OOM (that's how the tests simulate it, and what the kernel or the single runtime's memory limit does). opencode dies with Pixel (`agentsDieWithPixel`); on restart Pixel restarts it and sends a continue that doesn't count toward the limit. On Incus, opencode keeps running in the VM across Pixel restarts.
- Until a run starts, `runs.prompt` holds an optional per-run edited template body; afterwards the rendered prompt that was sent.
- Template sections (2026-10-15): `templates/parts/<name>.md` are Pixel's own, shipped with the code (environment, findings, report). A template uses one with `{{> name}}`; `render` expands sections first, then `{{#if}}` and variables, so sections can use both. Unknown section names are refused when saving a template version, creating one, or creating a run with an edited prompt. Because a started run stores the rendered prompt, editing a section never changes what old runs were sent. The Templates page lists the sections and can show the full prompt for an example run.

## Stats page (stats.ts)

- `GET /api/stats?days=1|7|30|90&tz=<minutes east of UTC>` → `/stats`. Buckets: hourly ≤ 2 days, 6-hourly ≤ 14, daily beyond, aligned to the viewer's clock via `tz`.
- Tokens come from the stored assistant messages (`json_extract` over `messages.data`), not `llm_calls`/`runs`, because those merge cache read and write into one `tokens_cache` column. That means history from before the page counts too; deleted runs drop out. Index `messages_created` is created by stats.ts.
- Cache hit rate = cache read / (input + cache read + cache write); opencode's `input` already excludes cached tokens. Savings ≈ cache read × (input price − cache-read price) for models in the models.dev catalogue (`costCacheRead`); custom endpoints aren't priced.
- Aborted calls (`MessageAbortedError`) aren't counted as errors. Tool stats come from `tool_calls` updated in the window.
- Health checks (runtime, data disk vs `PIXEL_MIN_FREE_GIB`, host memory, memory promised, event streams, provider errors in the last hour, backups) are computed on the server; the System page still holds machines and backups.

## API keys and failover

- Provider accounts hold `keys[]` in order; the first is the default. The API returns `PublicKey` (hint only, status only while it counts as failing).
- Each run's opencode gets its own key for its model's provider (`runs.key_id`, null = default); other providers get their default key. `credsStale` compares per run, so changing a run's key restarts its opencode when it is idle (directly, or in `onIdle` before the automatic continue).
- `runs/keys.ts`: classifies errors from `message.updated` errors, `session.error` and `session.status` retries. A failing key is marked on the account; the switch runs in the run's serial queue, so the idle event from the failed call can't send a second continue (`onIdle` also ignores idle events when opencode says the session is busy). Errors in the 30 s after a switch are ignored.
- Routes: `/providers/:id/keys` (POST add), `/providers/:id/keys/:key` (PUT edit, DELETE remove; runs on it fall back to the default), `/providers/:id/keys-order`, `/providers/:id/keys/:key/test`, `/providers/:id/keys/usage`; `/runs/:id/keys` (GET current key, next failover key, cost per key), `/runs/:id/key`, `/runs/:id/failover`.

## Findings (findings.ts) — added 2026-10-15, files instead of tools since the same day

- Replaces PROGRESS.md. The agent keeps one folder per finding in its workbase with its normal file tools: `findings/F<n>-<short-name>/README.md` starting with a `---` header (`state` lead | suspected | confirmed | ruled_out, `severity`, `location`, `poc` relative to the folder, `class`), then a `# title` and free markdown; PoCs and logs sit in the folder. A flat `findings/F<n>-name.md` is accepted too. No plugin, no API: other agents read the files. (The first version was an opencode plugin with `finding_add/update/remove/list` writing FINDINGS.json; dropped before any real agent used it, see decisions.md.)
- Pixel polls `findings/` every 5 s for active and just-finished runs (a readdir plus one stat per README; read only when names, mtimes or sizes change) and re-reads it right after a completed tool part whose input mentions `findings/F…` (that session becomes the finding's `session_id`). No `findings/` folder = nothing happens, so old runs are untouched.
- Sync diffs the files against the `findings` table: a new folder is an `add` event, a change of state, severity, title, location, PoC or class an `update` event with `{field: [old, new]}` (text-only edits just bump `updated`), a vanished folder a `remove` ("folder deleted"; it comes back as an `add`). Event time = the README's mtime. Each event is a timeline entry and a live `finding` message as before. Notes on state changes no longer exist (the reasoning is in the README).
- Bad headers don't drop a finding: the last good state/severity is kept and `findings.problem` says what's wrong (shown on the finding). Two folders with the same number: the one already known (else the first by name) keeps `F<n>`; the other gets its folder name as id plus a problem.
- Pixel writes `FINDINGS.md` (index table: id, state, severity, linked title, location, verdict) after every change and verdict, and `TRIAGE.md`. It never writes inside `findings/`. `findings.path` is the README path relative to the workbase; `poc` is stored workbase-relative.
- Triage (2026-10-20, replaced the verdicts): Pixel's own columns, never touched by the sync. `disposition` (report | known | duplicate | weak | invalid) with `disposition_note/at/by`, `severity_final` (null = agrees with the agent's `severity`; `none` = no impact), `duplicate_of` (`<run>/<id>`, required for duplicate, must exist, not itself). `triageFindings` applies items one by one (partial: fields left out stay) and writes FINDINGS.md, TRIAGE.md, run.json, INDEX.md and TRIAGED.md once at the end; events are `triage`. Report starts `disclosure` = ready; leaving report clears an unsent disclosure and is refused while reported or fixed. `setDisclosure` (ready | reported | fixed | dropped; `report_url`, `reported_at` defaulting to now, `fix_ref`, `fixed_at`, `disclosure_note` required for dropped) only for report; `POST /runs/:id/findings/:fid/disclosure` refuses requests from MCP (`x-pixel-mcp-token`). Events `disclosure`. Older `verdict` events still render. Nothing triage-related messages the run.
- The agent may write `duplicate_of:` in a README header; it's stored as `agent_duplicate_of` (normalised to `<run>/<id>`), tracked like the other header fields, used when you pick Duplicate without naming one, and offered as "Mark duplicate".
- `TRIAGED.md` at the workbases root (`knowledge.ts` `writeTriaged`, called from `writeIndex` and at start): every triaged finding across runs grouped by repository, linking each README; the prompt's findings part tells agents to check it before writing a finding up and to use `duplicate_of`.
- Filters on GET /findings and /runs/:id/findings: `severity` (the agent's), `final_severity` (final else the agent's), `state`, `disposition`, `disclosure` (each with `none`), `duplicate_of`, `repo` (substring), `view` (triage | report | resolved | reviewed), `untriaged`, `triaged`, `q` (all words in title, location, class, summary, repo or `run/id`; quotes keep a phrase; title then location matches first). `verdict` is a 400 saying what replaced it. Rows carry `repo` from the run.
- Deadlines (2026-10-20): a sent finding's deadline is `deadline_at` (set by Extend) or `reported_at` + Settings `disclosureDays`; rows carry computed `deadline` and `deadline_warn_at` (minus `disclosureWarnDays`). `checkDeadlines` (hourly, and at start) sends one `deadline` notification per stage (soon, over), remembered in `deadline_notified`; a moved deadline or a new send resets it.
- Runs from a finding (`findingRuns.ts`, 2026-10-20): POST `/runs/:id/findings/:fid/runs` {kind check | variants, ref, model, size} creates a run of the same repo with `parentRun` = the finding's run (so its workbase is offered read-only) and a prompt override (`{{> environment}}` + the task; variants also `{{> findings}}` and `{{> report}}`), labelled "<run> F1 on latest" / "variants", with `runs.source_finding` and `source_kind`. A check answers in REPORT.md with a header (`result`, `commit`, `fixed_by`); `readChecks` (every 5 s for live and just-finished check runs, all at start) records it on the finding (`upstream_*` columns, an `upstream` event, a Pixel timeline entry); the same answer read again is ignored.
- "To triage" = suspected or confirmed, not removed, no disposition. Leads are ideas, not counted.
- A run's result comes from its triage (`knowledge.ts` `dispositionCounts` / `outcomeText`): "2 to report (1 high, 1 low)" by final severity, "nothing to report", or none before any. Same places as before (findings.outcome, TRIAGE.md, run.json, INDEX.md, workbases list, finished rows). Leaderboard: `real` = report + known + weak (duplicates count through what they repeat), `triaged` = those plus invalid, `report`, `costPerReport`; `verdicts` breaks them down. Stats: `runs.dispositions`.
- **Copy for LLM** (`findingShare.ts`, added 2026-10-16): the finding detail's "Copy for LLM" button copies one markdown text (`GET /runs/:id/findings/:fid/llm?purpose=`): target repo/ref/commit, the agent's state and severity, location, the triage and disclosure, the README verbatim, the PoC inline if text (32 KB), other small text files inline (8 KB each, 64 KB in all), a list of the rest, download commands, findings already triaged in the same repository (not for disclose), and a task by purpose: verify (default), disclose (default when ready to report: the maintainers' report), variants. Lists: `POST /findings/llm` {ids as run/id, purpose list | triage | verify | disclose | variants, title} gives the findings shown as one text grouped by repository, each README cut to share 160 KB, no download tokens; every Findings list has the button with a menu of purposes. Downloads need a token (user: the token goes in the copied text and only opens that finding's files): each copy mints a random `pxf_…` token, kept only as its sha256 in `share_tokens` (run, finding, expiry 7 days, last use), sent as `Authorization: Bearer`, never in the URL. `/api/share/<fid>.tar.gz` (the folder as `<fid>/…`, 200 files, 50 MB) and `/api/share/<fid>/files/<name>` (only names in the finding's file list) are answered before the login check; wrong/expired token 401, another finding 403. Deleting the run drops its tokens. Host is `PIXEL_PUBLIC_URL`, else the request's (forwarded) host. Bun.Archive writes `Bun.file()` entries as empty, so files are read into memory first.

## MCP server for outside agents (mcp.ts) — added 2026-10-17

- `POST /api/mcp`, MCP Streamable HTTP, stateless: no session id, JSON responses only (no SSE; every tool answers at once), `GET` answers 405 as the spec allows. JSON-RPC handled by hand (initialize, ping, tools/list, tools/call; notifications get 202), so no SDK dependency. Protocol version: the client's if known, else the newest.
- Auth (changed the same day): MCP access tokens only (`mcpTokens.ts`, table `mcp_tokens`), `Authorization: Bearer pxm_...`; the dashboard password and cookie don't open it, and tokens open nothing else. `/api/mcp` is answered before the dashboard login check in `index.ts`. Tokens are made in Settings, Agent access (`/api/mcp/tokens`, dashboard login): name, `read` or `full`, expiry (never, 30, 90, 365 days); shown once, kept as sha256 plus the last 4 characters; each tool call sets `used_at`, `used_tool`, `uses`. Revoke deletes the row. A read token lists and calls only the `readOnly` tools (no `pixel_api`), and `get_run` drops `attach`/`shell` for it (they carry the agent's opencode password). `pixel_api` refuses `/mcp...`, so a token can't make tokens. A request whose `Origin` host isn't Pixel's (or the forwarded host) is refused.
- Tools call the API handlers through `dispatch()` with a synthetic request carrying the caller's host headers (finding briefs link to the right address). So every tool behaves exactly like the dashboard and no logic is duplicated. Outputs are trimmed for an agent's context: compact runs and findings, ISO times, transcripts rendered as text with long tool output cut, stats without the chart series; every answer capped at 60k characters.
- `pixel_api` is the escape hatch: any method and path (not `/mcp`); its description carries the live route list (`routeList()` in the router).
- For agents outside Pixel only. Pixel's own run agents still get no Pixel tools (findings stay plain files, see decisions.md 2026-10-15), and they can't reach the dashboard port anyway.
